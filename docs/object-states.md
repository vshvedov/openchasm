# Scripted level-object transitions

The bundled manual describes `explode x y` as destroying the object at a map cell and `change x y type` as changing that cell's SPR type. The independently reconstructed [PanzerChasm procedure implementation](https://github.com/Panzerschrek/Chasm-Reverse/blob/master/src/server/map.cpp) applies `change` and `explode` as immediate procedure commands and advances an exploded model to the next level-object definition, resetting its animation and health. `explode` calls this destruction routine even for models with BLim 0. It does not infer a replacement from the `BlowUp` effect value.

`ObjectStates` tracks level-object placements by source map cell. Scripted `Explode` advances the object's raw map ID by one; `Change` selects a raw level-object ID between 163 and 226. Either transition preserves the placement's position, angle and flags, resets health to the new definition's nonnegative BLim, and emits a typed transition with old/new IDs and an animation-reset request. Raw IDs 131–162 are items; lower wall/empty IDs are not represented by this subsystem. It does not create objects in empty cells or infer what happens if a replacement definition is missing: such actions fail closed. The reference allows advancing beyond the last model, which appears to hide/remove it; removal is intentionally not inferred here.

`apply_batch` validates and stages all requested transitions atomically; if any target cell, ID or definition is invalid, it changes nothing. The session must coordinate this state with combat, visual meshes, collision, procedure links and moving-object positions. `set_health` and `set_position` are available for synchronization, but are not a replacement for a single authoritative object state. Scripted destruction does not itself emit ordinary shot/destroy link events. The procedure runtime and host must establish validated action ordering, activation timing and behavior for other simultaneous commands before enabling real script execution.

A standalone check against this installation's level 16 script applied process 7's five object transitions: the four `16_end_1.3o` cells (27,46), (28,47), (28,48), (27,48) advance from type 201 to type 202 (`dummy.3o`), even though their BLim is zero; `change 29 48 200` changes the dummy to `fch2.3o`. This validates object data wiring only: process 7 also contains wind, quake and unlock actions, and the full boss encounter is not yet implemented.
