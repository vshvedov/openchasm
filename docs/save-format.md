# Save envelope and content identity

`save_format` supplies bounded, in-memory primitives. It does not itself read or write files, reconstruct content, or implement a user-facing save feature. No game asset bytes are stored by the envelope or manifest.

Version 1.0 is eight-byte magic `OPCHSAVE`, little-endian u16 major and minor, 32-byte content identity, little-endian u32 payload length, opaque payload, and SHA-256 of all preceding envelope bytes. The payload is limited to 16 MiB; decoding rejects unsupported versions, truncation, trailing data, oversized payloads, checksum mismatch, and, when requested, content mismatch. SHA-256 is an integrity check, not authentication. Any future payload decoder must validate its own schema and bounds before changing live state.

A content manifest hashes an ordered, length-delimited canonical manifest: each normalized lowercase relative resource name is paired with an explicit missing marker or a byte length and SHA-256. Sorting makes insertion order irrelevant, and missing differs from present-but-empty. The host must include all actual gameplay dependencies and decisions, including resolved asset fallbacks, rules version, difficulty, and capability configuration; merely using the source label or map filename is insufficient. The streaming digest API trusts the caller's provided byte count and digest. Filesystem storage of already encoded blobs is provided separately.

`session_codec` adds a versioned UTF-8 JSON payload inside this envelope, capped at 4 MiB. Its current schema is version 2; version 1 is explicitly migrated with inactive source lights and a fresh light-tick epoch, while unknown versions and unknown fields are rejected. Integer fields retain the explicit u8/u16/u32/u64 and i32 ranges of snapshot DTOs; the two map-cell `usize` fields are restricted to 0..63 for cross-platform portability. Finite f32 values round-trip through the codec; non-finite values are rejected. Encoding is bounded while writing; decoding limits input before parsing and checks vector cardinalities afterward. JSON has no attacker-declared array lengths, though parsing can allocate more memory than the input size. Decoded snapshots are untrusted and must be restored through `Session::restore_from_baseline` against verified content; decoding alone does not validate gameplay semantics or authenticate the data. Future schemas require an explicit versioned decoder or migration and must not reinterpret version 1 in place.

`save_store` reads and writes opaque encoded bytes in a caller-supplied, already existing trusted directory. Slot names use only ASCII letters, digits, underscores and hyphens, reject Windows device names, and map to `.ocs` filenames. Reads are streaming and limited to the maximum envelope size; callers must still decode and validate their contents. Writes create a unique same-directory temporary file, write and sync it, then use [`std::fs::rename`](https://doc.rust-lang.org/std/fs/fn.rename.html) to replace the destination without first deleting the previous save. Failures before a successful rename leave the previous file in place and attempt to remove the temporary file. Concurrent successful writes are last-rename-wins.

On Unix the store also attempts to sync the parent directory after replacement; its outcome is explicitly reported because a sync failure happens after the new file is already visible. Directory durability is unconfirmed on Windows, where this implementation reports it as unavailable. Atomic replacement and crash durability ultimately depend on the operating system and filesystem, especially network or unusual filesystems; a crash may leave a temporary file. The directory and its ancestors must not be controlled concurrently by an adversary: name validation is not symlink or path-race protection. These primitives do not choose a save location or expose a user-facing save system.

The client rules identity `SAVE_RULES_ID` in `src/main.rs` must be bumped whenever authoritative simulation rules, snapshot interpretation, resource resolution, fallback behavior or startup-derived gameplay decisions change. Treat this as a required part of reviewing such changes; it is not generated from the executable. Initial fingerprint eligibility requires the constructed Session to restore its own snapshot and reproduce it exactly. That check does not validate fresh scene reconstruction, guarantee that every later state is restorable, or replace re-opening and tracing current content before loading a disk save.
