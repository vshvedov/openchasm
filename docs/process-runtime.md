# Experimental level processes

The fixed-tick runtime handles floor-cell and nearby `link` triggers, wall `move` and `rotate`, `lock` and `unlock`, `StartDelay`, `Speed`, `BackWait`, circular `waitout`, and `playani`. Wall targets use their original map grid cells, and a process can move multiple segments together. Activation attempts report accepted, locked, unsupported, busy, or missing outcomes; the session forwards accepted and locked outcomes to mission messaging.

`playani` emits `ProcessEffect::PlayAnimation { object_id }` on forward activation. The process runtime does not simulate object animation. A process containing another unsupported action is disabled as a whole, so neither animation nor lock changes are emitted from a partial execution.

## Opt-in vertical and cell effects

By default `ProcessRuntime::new` leaves `up` and `change` processes disabled. A host can use `with_capabilities` to opt in to wall elevation and/or cell changes only when it can apply every returned effect to authoritative simulation and presentation state. Wall indices remain stable: `up` does not remove or reorder wall segments.

`take_effects()` drains effects accumulated from direct link activations and simulation ticks. The host must drain and apply them during each simulation step, including effects from pickup, shot and destruction links. `WallElevation` reports the absolute raw offset from the starting wall height. `CellType` reports a raw map type for a specific cell. The host supplies the original 4,096 cell types in x-major order to enable `change`. The runtime snapshots the current cell type as it completes a forward change and emits it on return. Change timing and interaction between multiple processes targeting the same cell remain provisional. Providing the grid is not sufficient by itself: the host must also be able to replace all affected wall and object representations and collision state.

For `up`, the runtime emits height changes at each movement tick. The installed Power Station uses 80 or 96 raw units for gates and fences. Published reconstruction behavior uses 64 raw units per vertical tile and a player-clearance threshold of 80 raw units; both the precise vertical rendering and collision behavior still require comparison with the original. The host, not the process runtime, must update wall rendering, movement and shot collision to match each reported offset. The process runtime checks player obstruction for horizontal motion only; vertical pushing, crushing, enemies, and objects are not modeled.

The process parser requires an `up` target to resolve to a supported wall or opted-in object and a `change` to have a valid target cell and byte-sized raw type. Malformed actions, disabled capabilities, missing wall targets, speed overrides, unrecognized actions, or multiple transformations targeting the same wall disable the whole process. Multiple processes affecting the same wall or cell are not yet coordinated.

## Rotation and behavior limits

Each observed `rotate` action has five arguments: target cell x/y, pivot x/y in map units, and a signed angle. The [original editor documentation](https://github.com/Panzerschrek/Chasm-Reverse/blob/master/docs/CSM_EDIT.TXT) identifies the pivot as a global coordinate and the last argument as an angle, but does not specify its units or handedness. The implementation provisionally interprets it as signed degrees and rotates the wall around that pivot. Rotational travel time uses the largest endpoint's arc length and the same provisional speed conversion as a translation. The unit, sign, timing and original behavior require visual comparison against the game.

Moving solid walls are sampled along their horizontal path and stop before overlapping the player's preview collision circle, resuming when the obstruction moves away. Sampling and the 0.18-tile radius are provisional. Moving walls do not yet push or crush players, do not check monsters or objects, and do not implement exact `CheckGo`/`CheckBack` semantics. Initially locked processes can be unlocked by supported switch actions; key-gated processes consult the owning player's supplied key state. The game loop must synchronize that state after pickup. Lock changes currently occur on activation even when a start delay is set. Audio is not implemented. `check` reports how many initially unlocked moving processes are supported under its selected capabilities, not all runnable level logic.

The original level 06 file includes an action section after a commented-out process header; the parser reports it rather than silently assigning it to a different process. A real-data smoke test of Power Station verified that process 7 emits animation 58 and unlocks process 5; process 5 raises its wall to raw height 80, while processes 16 and 17 raise all target fences to 96. Synthetic tests cover event emission, disabled capabilities, reversal, unsupported mixed actions, rotation, triggers and horizontal obstruction. These checks do not establish original-game fidelity.

The running session opts into wall elevation effects. It renders offsets using 64 raw units per tile and disables player movement collision at 80 raw units; the original movement flag is restored as the wall lowers. The preview treats walls above the player's horizontal shot height as nonblocking for shots. These values follow the independent reference and the installed Power Station script comment. The preview supports provisional jumping, wall clearance and animation events; crushing and complete vertical collision remain unsupported.

`return` use links and `returnf` floor links reverse their target process without reactivating it or emitting a mission activation event. They leave an already closed/closing process alone, cancel a start delay, and reverse a currently opening or fully open process from its current progress. Locked and unsupported processes ignore returns. Link order is preserved when normal and return links share a cell. The timing and lock behavior follow the independently reconstructed [ReturnProcedure](https://github.com/Panzerschrek/Chasm-Reverse/blob/master/src/server/map.cpp); it still needs comparison against the installed game.

`ProcessRuntime::with_cell_data` allows callers to supply the x-major raw map-cell IDs separately from the `change`-effect capability. A move, rotate, or enabled up command targeting a verified empty cell has no geometric effect but retains a timed process phase. A missing wall for a non-empty or unknown cell remains unsupported, because it may refer to an unimplemented model or object. If `change` effects are enabled and a previously empty target changes type, that process is rejected on later activation until the cell is empty again. Local scripts use such dummy moves at (0,0), including level 05 process 14 and level 17 process 7; both exit timers were verified headlessly using the real maps and scripts. The caller must use `with_cell_data` to enable this behavior.

## Death zones and nonstop

`ProcessRuntime::with_hazards` opts into `death` actions and their `nonstop` modifier separately from wall elevation and `change` support. The caller must drain and apply `HazardActivated { process_id, zones }` and `HazardDeactivated { process_id }` effects to its authoritative world. Older constructors remain fail-closed. Every zone retains its inclusive min/max grid cells, original vertical bounds, and damage amount without truncation. Negative bottom height is the documented marker for fields that exclude the player. An unrelated unsupported action still disables the whole process.

For a supported process, activation emits zones immediately when StartDelay is zero, or when the delay expires. A non-nonstop zone is deactivated when forward motion completes or reverses; a nonstop zone remains active until another process locks it. Locking and failed activation never start new zones. The isolated runtime sends lifecycle events; it does not apply damage, choose an overlap policy for multiple zones, or simulate player/actor height. Zone-only stages use the reference's provisional `10 / Speed` seconds (default Speed 10); movement and timing need comparison with the original game. One-shot `nonstop` without any understood death zone is kept unsupported rather than pretending to handle another persistent effect.

The independent [PanzerChasm zone implementation](https://github.com/Panzerschrek/Chasm-Reverse/blob/master/src/server/map.cpp) uses inclusive x/y grid cells, z values scaled by 1/64 tile, negative bottom to exempt the player, and damage at three ticks per second. Its field storage clamps z bounds to signed-byte range and casts damage to an unsigned byte; the installed scripts contain z=128 and damage=400/500. This implementation preserves those raw values, leaving the eventual host to settle cadence and overflow behavior after original-game verification.

A headless check with the actual level 16 process file verified process 9 remains locked initially; after a **test-only** unlock it emits the expected `death 4 4 60 60 -1 128 100` zone and its mission timer completes. The real unlock process 7 still contains unsupported explode, change, quake and wind actions, so this does not establish that the boss encounter or level is playable end to end.

## Scripted object motion

`ProcessRuntime::with_objects_and_hazards` opts into moving source map objects as well as existing hazard effects. The host supplies a validated `ProcessObject` for each object it can update: the original map cell, position in map tiles, yaw in radians, elevation in raw script units, and a conservative horizontal blocking radius in tiles. A zero blocking radius designates a nonblocking object. Cells must be unique, match an authored item or level-object type, and not also identify a wall; invalid or duplicate input fails construction. Omit unsupported objects, and any process targeting one of them remains wholly unsupported.

Supported `move`, `rotate`, and `up` commands targeting supplied objects emit an absolute `ObjectPose { cell, position, angle_radians, elevation_raw }` every movement tick. The original cell remains the stable identity as the object moves. Rotation transforms both position around the authored pivot and object yaw; `up` changes elevation only. `object_pose` exposes the current runtime pose. The host must drain effects every simulation step and synchronize the renderer, pickup positions, shootable-object positions, and all relevant collision data. When an object is collected, destroyed or replaced, call `remove_object` with its original cell: active movement stops and future attempts fail closed. A host must not enable this capability if it cannot keep all affected representations synchronized.

Moving objects use the caller's radius as a provisional circular horizontal obstruction against the player. Movement stops before pushing the player and resumes when clear; objects with radius zero pass through. Object/monster interactions, 3D geometry, vertical blocking, pushing, and crushing are not modeled. Object-target processes with `Mortal`, `CheckGo`, or `CheckBack` remain unsupported because the original interaction semantics are not implemented. The same applies to unresolved object targets, duplicate object transforms, speed overrides and other unsupported actions. A cell type changed through the opt-in `change` interface invalidates motion that was bound to its previous object type. Multiple processes moving the same object concurrently remain uncoordinated.

A real-data smoke test of level 11 process 7 activated its authored switch and moved the object bound to cell (27,10) by two tiles, emitting pose updates. Synthetic tests exercise move/return, rotation, elevation, player obstruction, missing or invalid objects, changed/removed targets, and mixed-process fail-closed behavior. The installed Power Station scripts contain no object targets for `move`, `rotate`, or `up`; moving scripted objects occur in later campaign maps. Correct timing and visual behavior still need comparison against the original game.

## Wind process effects

`ProcessRuntime::with_wind` opts into wind as well as the object and hazard capabilities of `with_objects_and_hazards`. The host must apply `WindActivated { process_id, zones }` and `WindDeactivated { process_id }` to its authoritative wind field and resolve resulting displacement against collision. Other constructors leave wind scripts unsupported.

Each `wind` action must contain exactly six integers: inclusive minimum and maximum map-cell coordinates, followed by signed direction components. Coordinates must be within 0–63 and in ascending order; direction components must be within -128–127. A malformed action, or any unsupported action in the same process, rejects the entire process without effects. The seven-field wind in the installed level 12 process 26 remains unsupported until its extra parameter is understood.

Wind shares the hazard lifecycle: it starts when the process opens after any start delay, stops when a finite opening completes or reverses, and a `nonstop` wind remains active until its process is locked. Wind and death zones in the same process emit separate effects. Wind-only process duration currently follows the provisional hazard timing of `10 / Speed` seconds; consumers should not infer original-game timing from this approximation.
